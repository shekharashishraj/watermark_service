Veripheye · 3D scene change detection prototype

Scene Change 3D

Compares a new walkthrough of a property against a 3D baseline of an earlier one and reports what went missing, what was added, moved or restyled, and which areas nobody checked. Everything runs on CPU and is measured on a synthetic apartment harness with exact ground truth.

Submitted proposal · robustness and calibration

Robustness under capture degradation

How robust are 3D change detectors to realistic sensor and observation degradation, and do their change scores show when they are wrong? Every held-out walkthrough is degraded at increasing severity and each method runs on it against the same clean baseline. The ground truth does not change, because only the recording is degraded.

    Map compression: do small changes fail first?

    The baseline map fused with coarser Gaussians (fewer, larger splats). Share of visible changes found, split at the median object size.

    Safeguard: no all-clear from noisy depth

    The sweeps showed this prototype reporting "Guest-ready" while 8 changes were present, when the depth sensor was noisy. A clean verdict now needs at least 80% of the depth to agree with the baseline; below that it says "Not verified (poor depth)". The cut-off was set on the development scenes; below are the held-out ones.

    Agreement: share of depth points matching the baseline surfaces. All-clear counts are before → after the safeguard, of 5 held-out scenes; with nothing changed, an all-clear from a capture that could not have shown a change becomes "Not verified".

    Safeguard: no restyle flood from bad exposure

    Under strong under- or overexposure the colour comparison broke and flagged most surfaces as restyled. Clipped or crushed pixels and frames the colour fit cannot model now give no appearance evidence, and a clean verdict is withheld when most colours could not be compared. Held-out scenes with changes, safeguard off → on.

    The same study on PASLCD, with the authors' code

    A kit for a GPU machine. It runs the official O-SCD (online) and MV3DCD (offline) on degraded copies of PASLCD, patched only to save their continuous change maps, and scores them with these metrics.

    cd scene-change-3d && export WORK=/scratch/$USER/scd
bash gpu/setup.sh                          # envs, official code + patch, PASLCD
bash gpu/make_jobs.sh > "$WORK/jobs.txt"   # method × scene × stressor × level
sbatch --array=1-$(wc -l < "$WORK/jobs.txt")%8 --export=ALL,WORK=$WORK gpu/array.sbatch
bash gpu/report.sh                         # same report, for PASLCD

    Details in gpu/README.md. The full report for the harness is ROBUSTNESS.md.

    Paper re-implementation

    O-SCD: online 3D scene change detection

    Galappaththige et al., CVPR 2026 (arXiv:2511.12370, official code). It detects changes from RGB frames alone against a reference Gaussian splat, fusing noisy per-frame cues into a 3D change field. Implemented in scene_change/oscd.py with the paper's hyperparameters and the real SAM 2.1 encoder running on CPU.

    Locate each frame

    Match keypoints against the 4 best reference keyframes, PnP-RANSAC, then pose refinement.

    SameMutual-NN matching at cosine 0.82, F-matrix outlier removal, top-4 keyframes
    AdaptedSIFT instead of XFeat, 3D points from reference depth, odometry fallback when PnP fails

    Change cues

    Render the reference at that pose and compare: C = Cpixel + Cfeature.

    Same0.8·L1 + 0.2·(1 − SSIM), SAM 2.1 hiera-tiny embeddings, the official renormalisation
    AdaptedONNX export of the encoder on CPU, about 1 s per image

    Change field

    Reference Gaussians carry a learnable change value, trained online with the self-supervised loss.

    Same16 Adam steps per frame, lr 0.0025, 67% replay of past frames, mask where M > 0.5
    AdaptedShapes frozen so rendering is linear (exact gradient without a GPU rasteriser); no densification

    Scene update

    Remove Gaussians inside changed regions and rebuild those regions from the new visit.

    SamePrune Gaussians blended into eroded change pixels in more than one view
    AdaptedRebuild from RGB-D instead of 5,000 photometric steps; keep surfaces hidden behind new objects

    Why it struggles here

    Three frames: a close-up of floorboards with no change, a room with no change, and a room with a removed table, lamp and side table.

    Inspection frameReference renderPixel cueSAM 2.1 feature cueCombined cueTrue change
    • Lighting differs between visits. The second walkthrough is 23% darker, with different room lamps. The paper corrects lighting only in its scene-update step, so both cues fire on unchanged surfaces. Global exposure matching recovers part of it.
    • Our reference renders are blurrier than a trained 3DGS. The depth-fused map cannot show floorboard grooves, which the pixel and feature cues read as change. A perfect render raises F1 but not the false alarms, because lighting still differs.
    • Feature-based localization is weak on these images. At 160×120 with low texture, 28% of frames fail PnP and fall back on odometry. Real phone video has far more texture.

    Scene update

    Fidelity of the map to the new visit (PSNR on its frames, higher is better).

    With correct change masks the update repairs changed regions (+8.3 dB) and leaves the rest alone. Noisy masks rebuild most of the map.

    Run the official code on this harness

    Writes a scenario in the official data layout (COLMAP model, reference .ply, true change masks) for a GPU machine, then scores its masks with the same metrics.

    python -m scene_change export-oscd runs/s003_mixed --out runs/s003_mixed/oscd_data
python oscd.py --source_path runs/s003_mixed/oscd_data ...   # official repo, on a GPU

    License check: the official repository has no license file and its files carry Inria's non-commercial terms. This implementation shares no code with it.
